# Off-the-shelf IdP evaluation: identity plane for belt + suspenders + buckle (W151, 2026-10-01)

Owner question: which off-the-shelf identity provider should the stack adopt so
belt/suspenders/buckle never build user management? Architecture thesis under
test: ONE OIDC IdP owns the human-identity plane — users, orgs/teams, roles as
claims, sessions, SCIM provisioning, admin UI, credential reset — while our
three services become resource servers validating its JWTs. Machine auth
(lane/service keys, budgets, spend) stays ours on the W132 v8 tables plus the
W149 issuer.

Two deployment modes follow from the brief:

- **Stack-native**: our IdP is the identity plane; services validate its tokens.
- **Corporate-mandated**: target-enterprise deployments may mandate a corporate
  OIDC provider; the stack then runs in pure resource-server mode validating
  externally-issued JWTs, and the IdP choice is skipped entirely (or reduced to
  a thin broker for local break-glass accounts). The resource-server validator
  is the same middleware in both modes.

Method / tiering: T1 = raw LICENSE files, GitHub REST repo metadata, and
official docs pages fetched directly (2026-10-01). T2 = official docs read via
search-result snippets, marked where used. Repo `pushed_at` values are GitHub
API facts at fetch time.

## 1. License ground truth (one brief correction)

**The brief expected Zitadel = Apache-2.0. T1 says otherwise: the
`zitadel/zitadel` LICENSE file is AGPL-3.0.** Zitadel relicensed Apache-2.0 →
AGPL-3.0 effective with v3 (announced March 2025; also standardized on
PostgreSQL, dropping CockroachDB). The repo's LICENSING.md keeps Apache-2.0/MIT
exceptions for specific directories, and the licensing FAQ confirms the SDKs
and proto definitions stay Apache-2.0 — so integrating over the API (generated
clients, HTTP/gRPC calls from our Bun/TS services) never triggers AGPL.

What AGPL-3.0 means for us, per the official FAQ:

- Self-hosting **unmodified** Zitadel as a separate network service: generally
  permissible.
- Any patch we make to the IdP itself must be shared.
- Distributing it inside a proprietary product: needs a commercial license or
  counsel. Given the klh stack may become an enterprise product, this is a real
  (containable) risk, not a theoretical one.

Everything else: **authentik = MIT core** (T1 LICENSE; carve-outs:
`authentik/enterprise/` under an EE license, `website/` under CC BY-SA 4.0) —
the cleanest license in the field. Keycloak, Ory (Kratos/Hydra/Keto), Casdoor,
SpiceDB, OpenFGA = Apache-2.0 (T1 LICENSE files). Logto = MPL-2.0 (file-level
copyleft; fine for aggregate server-side use — moot, because Logto has no SCIM,
below).

Read-out:

- Only **authentik** and **Casdoor** ship free SCIM in both directions.
  **Zitadel** has free inbound SCIM but users-only. **Keycloak's free path
  died at KC21; Ory's SCIM is paywalled; Logto has none.**
- Upstream OIDC brokering (the Entra-federation column) is table stakes — every
  finalist does it. The differentiator is **inbound SCIM with first-party
  corporate-IdP guides** (pre-provisioning and, more importantly,
  de-provisioning of departed users), where authentik is strongest and Zitadel
  covers users only. Even without SCIM, brokering alone de-provisions safely:
  a user the corporate IdP no longer authenticates simply cannot log in, and
  existing sessions expire.
- Maintenance: every candidate is alive (all pushed within the last two
  months), so this is not a dormancy pick like the W128 gateway audit — it is
  a license + fit pick.

## 3. Resource-server fit (Bun/TS)

Identical middleware regardless of issuer: fetch the OIDC discovery document,
verify `iss` against an issuer allowlist, `aud` against our client/app id, an
optional required roles claim, reject with 401 + a fixed error message; RS256
via JWKS. `jose` runs on Bun's WebCrypto. Conventions stay ours either way:
coarse `READ_`/`WRITE_`-prefixed scopes, `<platform>:<resource>:<role>` role
naming, two token classes (application-identity machine tokens via
client-credentials vs delegated user tokens), and strict environment isolation
(dev/test/ppe/prod, no cross-environment connections). Every finalist issues
service-account tokens, so the W149 machine plane does not depend on the IdP
choice.

## 4. Verdict

1. **authentik — RECOMMENDED.** License-cleanest (MIT core — a proprietary
   layer around it is uncontroversial, even embedded), the only candidate with
   free SCIM **in and out** plus first-party corporate-IdP federation guides,
   complete REST API, very active. Costs: heaviest of the light tier (server +
   worker + Redis + Postgres) and an org model of groups/roles rather than
   first-class multi-org — fine for per-customer installs, would matter for
   multi-tenant SaaS.
2. **Zitadel — runner-up.** Choose it over authentik when first-class
   orgs/teams, OpenID-Foundation-certified interop, or the smallest footprint
   dominate and AGPL is acceptable under containment rules: run unmodified as a
   separate network service, publish any patches, integrate only via the
   Apache-2.0 SDKs/protos, buy the commercial license before any product
   embedding. Its 2025 Apache→AGPL relicense is governance risk: the field has
   demonstrated it will flip.
3. **Keycloak — fallback** only when "Apache-2.0 + largest community" outweighs
   JVM ops weight and the missing free SCIM.
4. **Casdoor — budget wildcard**: right license, SCIM both ways, but thinner
   governance and polish; security-review before trusting it on a product
   surface.
5. **Skip**: Logto (no SCIM anywhere), Ory OSS (headless + SCIM paid; Keto
   stays interesting later, below).

**ACL stores: do not add SpiceDB/OpenFGA now.** IdP claims carry coarse roles;
fine-grained decisions live in our W132 v8 tables (precedent: the knowledge
hub's domain scoping). Revisit trigger: cross-customer relationship graphs that
outgrow plain table checks.

**When we'd skip the IdP entirely:** corporate-mandated deployments — pure
resource-server mode. Our services validate the corporate issuer's JWTs
(discovery + issuer allowlist + audience + roles claim); our own IdP is either
undeployed or reduced to a broker for local break-glass accounts. Nothing in
W141/W149 changes shape in that mode.

## 5. Shrink estimate (W149/W141)

- **W149 (JWT identity): ~40–60% becomes config-or-deleted.** User sessions,
  password reset, MFA, refresh-token rotation, and a revocation surface are IdP
  features. What remains ours: the resource-server validator middleware, the
  machine-plane issuer for lane/bootstrap tokens (the "forever token"), and
  belt's auto-refresh client — the same logic serves the corporate-IdP mode.
- **W141 (buckle governance): ~25–35% shrinks.** The "teams" third — org
  membership, invitations, roles CRUD, roles→claims — becomes IdP config plus a
  claims mapper. API keys, budgets, spend, and audit rows stay ours (gateway
  tiers + W132 v8 tables).
- **New cost:** one more service to run (authentik adds Redis to Postgres),
  per-deployment federation config, claims→policy mapping. Net clearly positive
  on generic deployments; zero effect in corporate-IdP resource-server mode.
