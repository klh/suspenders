# LiteLLM enterprise-capability audit for belt (W126, 2026-10-01)

Method / tiering: T1 = primary source fetched (docs.litellm.ai live pages) or
read directly from OUR pinned install's source tree (the strongest possible T1
for version applicability: the code we actually run). T2 = corroborating
secondary (search snippets, third-party write-ups). The local install is
LiteLLM **1.103.0** (uv tool install, `litellm` + `litellm_enterprise` 0.1.69 +
`litellm_proxy_extras` 0.4.100 in the same site-packages), fronted by belt's
gateway on loopback :4100 (launchd wrapper in belt `bin/gateway.ts`, config
generated by `bin/gateway-config.ts` into the private `~/.claude/local-llm/`
litellm.yaml — keys resolved from env at spawn, master key from the key file;
nothing key-shaped appears here). Where the live docs describe a feature we
could not confirm in the 1.103.0 tree, the row says so.

Ground truth from our generated config: model_list maps OpenAI-shape local MLX
specialists (four ports), one LAN Ollama box, the z.ai GLM family twice
(`openai/` against z.ai's OpenAI endpoint and `anthropic/` against its
Anthropic-shape endpoint), and `anthropic/claude-*` at api.anthropic.com;
`router_settings` = latency-based-routing, num_retries 1, cooldown_time 30;
belt also runs an Anthropic-shape ingress shim on :4000 for `claude -p`
traffic (excluded from the gateway's model_list by design).

## 2. License boundary

LiteLLM = MIT core + a closed, license-gated `litellm_enterprise` package that
ships inside the same pip/Docker build (T1: both present in our
site-packages). Enterprise features check `LITELLM_LICENSE` ("eyJ...")
at runtime and no-op without it; docs note the proxy reports "Enterprise
Edition" on its docs page when active. Self-hosted: "No data leaves your
environment."

Pricing model (T1, litellm.ai/pricing, fetched 2026-10-01): two tiers only —
Open Source $0 ("free forever, self-hosted"; FAQ: no license fee for
production use of the OSS gateway) and Enterprise "talk to sales". Enterprise
is NOT per-seat and NOT per-token: "priced to your gateway's scale, never per
token" — annual contract sized by "annual gateway request capacity,
deployment architecture, and support needs". No public dollar figures. 30-day
trial key by email, no card. Procurement: direct, AWS Marketplace, Azure
Marketplace, resellers. Included support: business-hours Slack/Teams channel;
24/7 SLAs cost extra (Sev 0: 1 h, Sev 1: 6 h, Sev 2-3: 24 h).

Boundary summary: identity beyond static bearer keys (SSO beyond 5 users,
SCIM, JWT), compliance (audit logs, retention), org tenancy (orgs, org/team
admins, RBAC), ops-hardening (key rotation, secret managers, multi-region,
region-outage alerts, managed-batch metrics) are paid. Everything that makes
a fleet economically sane — virtual keys, budgets, rpm/tpm, spend tracking,
alerts, fallbacks, caching, all routing strategies, Prometheus, guardrail
mechanism — is free.

## 4. Belt exposure design (belt as the thin layer)

Division of labor on top of the :4100 gateway:

- LiteLLM owns (config, no code): transport to all backends, retries,
  cooldowns, fallback ladders, rate limits, budgets, spend tracking, caching,
  metrics, guardrail execution.
- Belt owns today (and should keep): the resolution chain (resolveBelt:
  env → local belt.json → probe → dev default, named-service not address —
  knowledge k#108), route policy scoring from its own metrics.db with a
  product-grade audit table for allowed AND denied decisions (route-policy.ts
  POST /api/route, bearer-token product surface), the Anthropic-shape ingress
  shim for `claude -p`, the MLX spawner/registry, WoL-ensure before LAN
  gateway calls, prefs (cost_speed, allow_cloud).
- Belt adds (new, thin): (a) key-issuing UX — call `/key/generate` per
  consumer/lane and hand out virtual keys instead of the single master key;
  (b) route-hint grammar mapped to model groups (a hint like "cheap"/"local"
  resolves to a group name, not a port); (c) the policy file stays belt-side
  and is projected INTO the generated litellm.yaml by gateway-config.ts.
- Enterprise install story:
  - 50-dev org: OSS only. Postgres + master key; one virtual key per team/app
    with budget + rpm/tpm; Slack budget alerts; Prometheus scrape; admin UI
    behind basic auth on loopback/Tailscale; fallback ladder in config. Zero
    license, zero belt-specific code.
  - 3000-dev org: add the enterprise license — SSO/SCIM so humans stop
    handling keys, JWT auth for service accounts (claim→team mapping), audit
    logs for compliance, org/team admin RBAC, key rotation with grace, secret
    managers, Redis for multi-instance rate-limit + cache state, guardrails
    scoped per key/team, multi-region if needed. Belt unchanged: it still
    holds one virtual key per consumer; the license unlocks identity and
    compliance layers, not new plumbing.
  - The upgrade path is continuous: same config schema, add
    `LITELLM_LICENSE`; belt does not change shape between the two.

## 5. IKEA-fit verdict

Does the virtual-key/budget/tenancy layer close the authn + quota gap from
the org-scale assessment?

- Quota gap: CLOSED, entirely in the free tier. Per-key/per-team budgets,
  soft budgets with projected-exceed alerts, rpm/tpm per key and per model
  group, spend tracking per key/team, Prometheus budget gauges. This is the
  part W124 was going to hand-build; it is config + a Postgres URL.
- Authn gap: MOSTLY CLOSED, with a tier line. Free tier = static virtual keys
  - master key + admin UI basic auth: fine for a fleet of agents holding
    issued keys, insufficient for human SSO. Human identity (SSO beyond 5 UI
    users, SCIM, JWT service-account auth) sits behind the license. For an
    agent-fleet (no humans at the API surface) the free tier is arguably
    sufficient; for a 3000-dev org it is not, and the license is the price of
    identity, not of quota.
- Outside LiteLLM, stays ours:
  - Knowledge-tier ACLs: LiteLLM has no concept of document/knowledge ACLs;
    knowledge.db row-level access stays a suspenders concern.
  - Control-plane auth: W92's store-server token on :7794 guards the work
    graph, not LLM traffic — different plane, keep the x-governor-token
    mechanism.
  - Belt's product layer: resolution, scoring, audit trail, complexity
    tiers, cloud gating, local-spawner lifecycle. LiteLLM replaces none of
    it; it removes the retry/fallback/quota code belt would otherwise grow.
- Verdict: HIGH fit for the quota/rate-limit/fallback/observability tier
  (pure config on the already-running 1.103.0 gateway; only new dependency
  is Postgres for virtual keys). MODERATE for tenancy — teams are free,
  orgs/RBAC are paid, and agent fleets mostly need teams. LOW fit for
  knowledge ACLs and control-plane auth — wrong layer, keep in suspenders.
