## 0. Thesis: families, not providers

LiteLLM carries 100+ provider adapters because the world speaks many dialects
(W129 §1 row 3: `llms/` is 208k LOC across 950 files). We ship five FAMILIES,
two of which are pass-through:

1. `openai-compat` — one generic adapter covers OpenAI, z.ai, OpenRouter,
   vLLM, LM Studio, one-api-class shims, and local MLX/Ollama servers.
2. `anthropic` — the Messages API family.
3. `azure-openai` — the OpenAI dialect with a URL/auth profile.
4. `bedrock` — its own dialect (Converse), sigv4 auth, binary event stream.
5. `vertex` — its own dialect (Gemini `generateContent`), gcp oauth.

Provider = a data row, not code. LiteLLM reached the same conclusion in the
pinned install: `llms/openai_like/providers.json` declares 28 whole providers
as config (`base_url`, `api_key_env`, `param_mappings`, `special_handling`)
consumed by `JSONProviderRegistry` (`openai_like/json_loader.py:27`, `:39`,
`:64`) — LiteLLM's own long tail stopped being code. We copy that: tier-3
providers are YAML rows, never new adapters.

## 1. The adapter interface (TS)

Port of LiteLLM's `BaseConfig` ABC
(`llms/base_llm/chat/transformation.py:69`), reshaped for pass-through-first:
the pass-through families implement almost nothing (identity transforms +
URL/auth), so identity must be free, not inherited overhead. `BaseConfig`
anchors ported: `get_supported_openai_params` :187, `map_openai_params` :237,
`validate_environment` :247, `sign_request` :259, `get_complete_url` :284,
`transform_request` :305, `transform_response` :337, `get_error_class` :365,
`get_model_response_iterator` :368.

```ts
export type AdapterFamily =
  "openai-compat" | "anthropic" | "azure-openai" | "bedrock" | "vertex";

export interface WireCall {
  url: string;
  headers: Record<string, string>;
  body: string; // wire JSON, ready for fetch
}

export interface ChatAdapter {
  family: AdapterFamily;
  /** wire shape spoken on the upstream leg once buildCall is done */
  dialect: "openai" | "anthropic";
  /** per attempt: URL + auth (may refresh tokens) + body patches.
   *  Pass-through families patch only (model id, stream_options);
   *  transform families rewrite (Converse, generateContent). */
  buildCall(up: Upstream, req: IngressRequest, body: string): Promise<WireCall>;
  /** non-streaming reply → router's canonical response (identity for
   *  pass-through families) */
  parseResponse(up: Upstream, wire: unknown): unknown;
  /** status/body/headers → normalized RouterError (errors.ts) */
  normalizeError(status: number, wire: unknown, headers: Headers): RouterError;
  /** usage extraction, streaming tee + non-streaming path */
  usageOf(wire: unknown): UsageDelta | null;
  /** capability flags the router advertises and enforces */
  readonly caps: {
    countTokens: boolean;
    tools: boolean;
    streamOptions: boolean;
  };
}
```

Design rules:

- **Pass-through is the identity case.** `openai-compat` and `anthropic`
  return the body with minimal patches; `parseResponse`/`usageOf` on
  pass-through families read fields, they never re-serialize the client leg.
  The router pipes upstream SSE to the client verbatim (W131 §1); the tee is
  passive.
- **Auth lives inside `buildCall`** — the same seam LiteLLM draws with
  `sign_request` (`transformation.py:259`). Bearer families set one header;
  bedrock signs; azure/vertex may refresh a cached token. Refresh failures
  normalize to `auth` errors, never crash the attempt loop.
- **Every error surfaces normalized.** No family-specific exception types
  reach the router or the ladder.

`RouterError` taxonomy (`src/adapters/errors.ts`), shaped so the ladder's
retry policy can key on it (W131 §2 item 2):

| normalized   | retryable | openai-compat                          | anthropic                                        | azure-openai         | bedrock                                             | vertex                   |
| ------------ | --------- | -------------------------------------- | ------------------------------------------------ | -------------------- | --------------------------------------------------- | ------------------------ |
| rate_limited | yes       | 429                                    | 429 `rate_limit_error`                           | 429                  | 429 `ThrottlingException`                           | 429 `RESOURCE_EXHAUSTED` |
| overloaded   | yes       | 503 (some backends)                    | 529 `overloaded_error`                           | —                    | —                                                   | 503 `UNAVAILABLE`        |
| timeout      | yes       | 408 / abort                            | abort                                            | abort                | 408 / abort                                         | abort                    |
| auth         | no        | 401/403                                | 401 `authentication_error`                       | 401 (Entra denied)   | 403 (sigv4 rejected)                                | 401/403 (token rejected) |
| bad_request  | no        | 400/404/422, `context_window` subclass | 400 `invalid_request_error` (context/max_tokens) | 400 + content_filter | 400 `ValidationException`, `ModelNotFoundException` | 400 `INVALID_ARGUMENT`   |
| server       | yes       | 5xx                                    | 5xx                                              | 5xx                  | 5xx `ServiceUnavailableException`                   | 5xx `INTERNAL`           |
| network      | yes       | fetch throw                            | fetch throw                                      | fetch throw          | fetch throw                                         | fetch throw              |

`retry-after` (header or body `error.metadata`) populates `retryAfter`; the
ladder honors it before jittered backoff (W131 §2 item 2, LiteLLM
`_calculate_retry_after` semantics per W129 §2).

## 3. Port tiers + per-adapter effort

Sizing per W131 §4 (S ≤ ~150, M ~150-400, L > 400; LOC = implementation +
inline tests). The thin slice (tier 1) is inside W131's phase-1 estimate
already — these numbers are the adapter layer only.

| Adapter                         | Tier | Size | LOC         | Cost driver                                                                                                                                                                           |
| ------------------------------- | ---- | ---- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| openai-compat (generic)         | 1    | S    | 40-80       | identity patches: model id, `stream_options` injection; usage fields `prompt/completion_tokens`                                                                                       |
| local profile (MLX/Ollama/vLLM) | 1    | S    | 0-40 (data) | openai-compat + a quirks object: discovery, `include_usage` often ignored, thinking flags, tool support varies — data flags, NOT a new adapter                                        |
| anthropic                       | 1    | S    | 40-80       | pass-through + count_tokens forward + cache-token usage kinds                                                                                                                         |
| azure-openai                    | 2    | M    | 120-220     | deployment URL shape + api-version query + api-key/Entra header profile; Entra client-credentials refresh ~60-80 LOC                                                                  |
| bedrock                         | 2    | L    | 350-550     | sigv4 (vendored), Converse dialect transform, and the REAL cost: Converse-stream uses the AWS binary event-stream framing, not SSE — frame parsing + CRC ~150 LOC vendored or written |
| vertex                          | 2    | L    | 300-500     | gcp service-account JWT (RS256 via WebCrypto) → token exchange → expiry cache + single-flight refresh (~120-150) + Gemini dialect transform (~120-180)                                |
| tier-3 long tail                | 3    | —    | 0 code      | YAML rows per the `providers.json` precedent; a provider that needs logic beyond `param_mappings` becomes an adapter proposal, not a row hack                                         |

Adapter-layer total: ~550-1.2k LOC on top of W131's ~1.7-2.9k.

### 3.1 Auth is the real cost (honest note)

Bearer keys (openai-compat, anthropic, z.ai, OpenRouter): trivial. The
enterprise clouds are tier 2 BECAUSE of auth, not wire shapes:

- **bedrock sigv4**: vendor `aws4fetch` (ISC license, single file, WebCrypto,
  Bun-native, no deps) WITH its LICENSE + NOTICE vendored alongside —
  license-clean. Own-implementation fallback is ~80-120 LOC + AWS test
  vectors, justified only if vendoring is politically unwanted.
- **vertex gcp oauth**: `google-auth-library` drags gaxios and friends —
  over-weight for one token flow. Spec a ~120-150 LOC service-account flow:
  RS256 JWT via WebCrypto → token endpoint exchange → cache keyed on
  (project, scopes) with expiry-minus-skew refresh + single-flight lock
  (LiteLLM's lock at `vertex_llm_base.py:90-92` exists for exactly the
  stampede we would create).
- **azure Entra**: api-key header is trivial; the optional Entra path is a
  client-credentials POST (form-urlencoded) + cache — ~60-80 LOC, no SDK.
- **never**: any `litellm_enterprise` import, path, or file (W126 boundary).
  Attribution: ported MIT code carries the LiteLLM copyright notice in
  `NOTICE` (buckle already has `NOTICE.md`), transform tables cite the
  source anchor in a comment.

### 3.2 What we deliberately do NOT port

Per-model cost JSON (2.8 MB — 4-entry table instead), model-info registry,
guardrail translation, `invoke`/`messages` Bedrock APIs alongside Converse
(Converse only), provider inference (`get_llm_provider`), 100-provider
dispatch, response-API/multimodal surfaces. Each is a LiteLLM compat tax for
being universal; buckle is configured, not universal.

## 4. Framework layout, policy naming, tests

### 4.1 File layout (`buckle/src/adapters/`)

    src/adapters/
      types.ts         # ChatAdapter, AdapterFamily, WireCall, Upstream, UsageDelta
      errors.ts        # RouterError enum + retryable/retryAfter + family mappings
      sse.ts           # line splitter + event framing helpers for the tee
      tools.ts         # THE transform: openai tool_calls <-> anthropic tool_use (§5.1)
      openai-compat.ts # generic family (also serves local profiles via quirks)
      anthropic.ts     # pass-through + count_tokens forward + usage kinds
      azure-openai.ts  # openai-compat + URL/auth profile
      bedrock.ts       # Converse transform + sigv4 (vendor) + eventstream decode
      vertex.ts        # Gemini transform + gcp token flow
      index.ts         # registry: getAdapter(family) — unknown = startup fatal

Sits next to what exists: `src/{policy,upstreams,ledger}.ts`; the router
(w131-phase lane) consumes adapters through `getAdapter`.

### 4.2 How the policy names adapters

`upstreams.yaml` gains one field per deployment: `adapter:`. Backward
compatible by construction — absent `adapter` derives from today's `dialect`
(`openai` → `openai-compat`, `anthropic` → `anthropic`), so the committed
file needs no migration:

    groups:
      claude-sonnet-5:
        - url: <provider-base-url>
          adapter: anthropic
          api_key_env: ANTHROPIC_API_KEY
      corp-azure:
        - url: <azure-endpoint>
          adapter: azure-openai
          model: gpt-5.2            # deployment name
          adapter_config:
            api_version: "2026-03-01-preview"
            region: <region>
      corp-bedrock:
        - adapter: bedrock
          adapter_config:
            region: <region>
            model_id: <model-id>

Rules:

- `adapter_config` holds family parameters (region, project, api-version) —
  secrets stay in env vars named in `api_key_env` (committed-file rule:
  never keys, never private hostnames — placeholders only).
- Unknown `adapter:` value = startup fatal with the offending group named.
- `adapter` is per-DEPLOYMENT, not per-group: a group can mix families (e.g.
  `local-swarm` openai-compat + one anthropic deployment), and the ladder
  stays family-blind — the adapter layer is where dialect differences stop.

### 4.3 Test strategy per adapter

| Adapter       | Mock suite (always)                                                                                                   | Live (gated)                                           |
| ------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| openai-compat | recorded fixtures: tool-call fragments split mid-argument, usage-only final chunk, `[DONE]`, ping comments            | local MLX (free, always-on) as the live smoke          |
| anthropic     | golden SSE transcripts (message_start/content_block_*/message_delta/message_stop), cache-token usage, 429 retry-after | gated on env key; manual smoke only — per-request cost |
| azure-openai  | recorded Entra token exchange + URL/api-version assertions; content_filter error mapping                              | gated on tenant creds; manual                          |
| bedrock       | sigv4 against AWS published test vectors + tamper test; eventstream frames (CRC good/bad); Converse transforms        | gated on creds; manual                                 |
| vertex        | fake service account + local token endpoint: JWT shape, exp/skew, single-flight refresh race                          | gated on creds; manual                                 |

Cross-cutting:

- Mock upstreams are in-test `Bun.serve` on an ephemeral port — no external
  mock service, no network in CI.
- Every transform is golden-fixture: byte-identical output assertions on
  recorded transcripts; a provider drift shows up as a fixture diff, and the
  fix lands as a NEW fixture alongside the old one (history, not overwrite).
- The shim-tier prior art (`belt/bin/anthropic-shim.ts`, 98 lines,
  non-streaming, tools flattened, usage zeros) is the anti-pattern test case:
  its responses violate the W131 "never fake zeros" ledger doctrine and
  cannot stream or carry tools. Its replacement is `tools.ts` + the
  anthropic adapter, tested by the fixtures above.

## 5. Risks

### 5.1 The ONE transform: OpenAI tool_calls ↔ Anthropic tool_use

W131 §5 named cross-dialect tool calls "the single largest hidden surface…
the item most likely to bust the M estimate." Designed once, here, in full.
`src/adapters/tools.ts` is the only file allowed to know both vocabularies;
pass-through families import nothing from it.

Non-streaming mapping (request direction = toward an openai upstream from an
anthropic-dialect ingress, response = back):

| Anthropic                                                      | OpenAI                                                                                                                                                                    |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tools[] {name, description, input_schema}`                    | `tools[] {type:"function", function:{name, description, parameters}}`                                                                                                     |
| assistant msg `content[]{type:"tool_use", id, name, input}`    | assistant msg `tool_calls[]{id, type:"function", function:{name, arguments: JSON string of input}}`                                                                       |
| user msg `content[]{type:"tool_result", tool_use_id, content}` | one `{role:"tool", tool_call_id, content}` message per block (text before/after stays in the surrounding user message)                                                    |
| `tool_choice {type:"auto"/"any"/"tool", name?}`                | `"auto"` / `"required"` / `{type:"function", function:{name}}`                                                                                                            |
| `stop_reason: "tool_use"`                                      | `finish_reason: "tool_calls"`                                                                                                                                             |
| `stop_reason: "max_tokens"`                                    | `finish_reason: "length"`                                                                                                                                                 |
| `stop_reason: "end_turn"/"stop_sequence"`                      | `finish_reason: "stop"`                                                                                                                                                   |
| response `content[]{type:"tool_use"}`                          | `message.tool_calls[]` with `arguments` JSON.parse'd → `input`; parse-fail → text block with the raw string + ledger warn (reject-verbose, never silent mangle — W131 §5) |

Streaming event mapping (both directions; the tee-side of `tools.ts`):

| OpenAI chunk                                       | Anthropic event emitted                                                                                                                                                              |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| first chunk (buffered to synthesize envelope)      | `message_start` (id, model; `input_tokens`: real when upstream sent usage, else wire-schema minimum with ledger `usage: unknown` — ledger never fakes, wire schema must still parse) |
| `delta.content` fragments                          | `content_block_start` (text) + `text_delta` fragments + `content_block_stop`                                                                                                         |
| `delta.tool_calls[i]` first fragment (id+name)     | `content_block_start` (`tool_use`, `id`, `name`, `input:{}`)                                                                                                                         |
| `delta.tool_calls[i].function.arguments` fragments | `input_json_delta` `partial_json` fragments, concatenated verbatim per index                                                                                                         |
| `finish_reason: "tool_calls"`                      | `content_block_stop`, `stop_reason: "tool_use"`                                                                                                                                      |
| final usage-only chunk (`include_usage`)           | `message_delta` (cumulative usage) + `message_stop`                                                                                                                                  |

Edge rules (each one is a fixture):

- Parallel tool calls: OpenAI interleaves by `index`; anthropic emits
  sequential blocks — transform orders blocks by first-seen index.
- `parallel_tool_calls` param has no anthropic equivalent toward this
  direction — drop + ledger warn.
- Unknown/untranslated params: reject-verbose (HTTP 400 naming the field),
  never silently mangle (W131 §5 "param long tail").
- Anthropic → openai direction mirrors the table; `system` string/blocks →
  `role:"system"` message; thinking → `reasoning_effort` where supported,
  honest degrade where not (W89.1 requirement 3).

### 5.2 Provider drift

- Drift is detected by fixtures, not by reading release notes: a changed
  upstream response fails the golden replay; fix = new fixture committed
  NEXT TO the old one (drift history is design documentation).
- Adapter upgrades are incident-driven, never bulk: the long tail stays data
  rows, so upstream churn in one provider cannot force an adapter release.
- LiteLLM is the drift radar even after adoption: when its changelog or
  per-provider transformations move for a family we carry, the fixture set
  re-checks against our port (MIT permits this; attribution stays).
- Wire-id `[1m]` note conflict (W131 §7): pass-through families never
  rewrite ids; the one transform's handling is pinned by a fixture, and the
  shadow week (W131 §4) settles it empirically.

### 5.3 Other risks

- **Mid-stream upstream death**: SSE `event: error` + close, no re-route
  (would duplicate content) — W131 §5, unchanged by adapters.
- **count_tokens gap**: only the anthropic family has a real endpoint;
  openai-dialect upstreams get the router's honest-estimate fallback, and
  `caps.countTokens=false` makes the router answer instead of forward.
- **context-window mapping**: `bad_request` + `context_window` subclass
  (LiteLLM splits it, `exceptions.py:534`) so the ladder can react
  (shrink/shim) rather than plain-fail — small, but wired into the enum.
- **Eventstream CRC failure mid-stream (bedrock)**: treat as `network`
  (retryable before first byte, `event: error` after), never partial output.

## 6. Verdict inputs and could-not-verify

W131 §6 rule 1 said "a third dialect in the pool flips the build case toward
fork" — this doc sharpens that: the flip trigger is a THIRD DIALECT THAT
SALES NEEDS, and the tier-2 answer prices that flip at ~550-770 LOC
(azure+bedrock+vertex), not at a fork. W130's Portkey-fork verdict stands
only if the adapter matrix — not governance — dominates; at five families
with two pass-through, belt-native + a tier-2 port list wins the W130 §5
pricing rule. Revisit if tier-3 demand starts demanding LOGIC (a provider
that cannot be a data row), not merely rows.

Could-not-verify:

- Exact SSE framing of Azure OpenAI streaming (assumed openai-compat
  identical; Entra-tokened deployments may emit different error bodies —
  unverified, fixture on first live contact).
- AWS eventstream frame format details (parsing headers/CRC) cited from
  LiteLLM's bedrock tree layout, not implemented/verified here — the bedrock
  estimate carries a vendoring assumption.
- gcp token endpoint behavior with workload-identity-federated credentials
  (service-account JSON flow speced; WIF is a later concern).
- z.ai 429 retry-after presence (W131 §7 open item — unchanged here).
- LOC figures are judgment estimates per W131 sizing, not derived from a
  decomposition exercise.
- belt `bin/anthropic-shim.ts` read for prior art (read-only); the belt repo
  is another lane's surface — no belt files were modified.
